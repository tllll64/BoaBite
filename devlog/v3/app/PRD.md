# BoaBite · PRD 产品需求

> 核心内容来自 2026-09-27 用户手写 PRD；产品落点与优先级已确认（§7）。
> 最后更新：2026-09-27

## 1. 目标用户

想要减肥，但管不住嘴的人。正向的，有积极戒掉的心里。

## 2. 核心场景

在正餐之外（多吃），每次想要吃多余的东西，但害怕吃了发胖有心里负担。

具体场景：

- 同事递来的小零食
- 一下子来一大块想要分给别人
- 逛超市想要加入购物车的零食
- 半夜嘴馋从冰箱拿点吃的
- 被朋友拉着去吃夜宵
- 看到免费的食物想吃一口

## 3. 用户的一天

**日常流程**：

起床 → 早餐 → 上午（上班&上学）→ 午餐 → 下午（下午茶）→ 晚餐 → 晚上（夜宵）→ 睡觉

**特殊流程**：

健身之后 / 朋友约饭 / 旅行 / ……

## 4. 问题洞察

**为什么想吃（原因）**：

| 类型 | 内容 |
|---|---|
| 生理 | 激素失衡、营养缺口、体力消耗 |
| 情绪 | 情绪性进食、限制思维反噬、大脑奖赏机制 |
| 环境习惯 | 外部线索自动触发 |

**为什么想吃但控制不住**：

理性脑知道客观认知，本能脑产生冲动，给出合理化借口。

## 5. 解决方法

❌ 靠意志力硬对抗欲望（相关被否决方案见 §9 排除清单）

按解决点罗列：

1. **分散注意力**——给一个代替出口，打破"吃 / 不吃"的二元选项（喂给蛇）
2. **元认知觉察**——标记设计（AHA moment：用户在"想吃"的瞬间被标记、被看见）
3. **心智反馈闭环**——轻量行为日志，收集借口样本
4. **正向反馈**——正向的、不评判的反馈体验

## 6. AI 能力在产品中的价值

> 一句话：AI 不是卖点，是让「喂蛇代替吃」这个核心机制真正成立的引擎。

| AI 价值点 | 对应功能 | 没有 AI 会怎样 |
|---|---|---|
| **信息与知识获取**：识别食物后即时呈现真实热量、健康影响等客观知识 | 食物识别 + 品鉴结果页（kcal / 份量 / 感言） | 用户对"这一口"没有真实认知，喂蛇退化为拍照计数 |
| **高效录入**：拍摄即完成全部录入 | 食物识别（菜名 / kcal / 份量） | 手动输菜名 + 查热量 → 记录疲劳 → 日记死掉 |
| **情感化陪伴**：不重样、不评判的品鉴感言，随人设切换风格 | 品鉴感官文案 + 蛇的人设 | 三次后看到固定话术 = 又一个说教工具 |

> 知识呈现的原则：**给事实，不恐吓、不说教**——热量是多少就是多少，健康影响讲清楚，结论留给用户自己得出（呼应"自行觉察"与正向调性）。

**边界（AI 不做什么）**：

- ❌ 不做专业化的饮食管理工具——营养建议、饮食管理不是这个产品的方向
- ❌ 不做日历/记录内容的总结——累计投喂多少次、多少热量，AI 不总结、不解读。用户通过完整的**蛇的形态**和自己的**真实记录**自行觉察；AI 代劳总结就太重了，等于替用户完成了觉察本身

## 7. 产品落点（已确认 2026-09-27）

| 优先级 | PRD 概念 | 对应功能 | 状态 |
|---|---|---|---|
| **P0** | 分散注意力 | **蛇的行为本身**——把东西喂给蛇，就是代替出口 | ✅已确认 |
| **P0** | 元认知觉察 | **点击拍照投喂的整个流程** | ✅已确认 |
| **P1** | 心智反馈闭环 | **投喂的日记记录**（月历 + 列表） | ✅已确认 |
| **P2** | AI 人设 | **蛇的人设可切换**：不同人设对应不同的文案表述，AI 生成链路中的品鉴感言风格也随之改变 | ✅已确认 |
| **第 2 期** | 第三方正向反馈 | **分享给好友**：对应的图片 + 忍住吃的过程；入口 = **投喂日记记录页右上角分享按钮** | ✅入口已定 · 实现缓做 |

> 分享功能：入口已定（记录页右上角按钮），会随设计一起呈现，但**实现优先级缓做**（P1+，原型期只做按钮占位，不接真实分享渠道）。

## 9. 功能排除清单（Feature Rejection Log）

> 明确被否决 / 不做的功能点，防止后续讨论反复回炉。用户将逐条口述，持续登记。

| 日期 | 排除项 | 原因 |
|---|---|---|
| 2026-09-27 | 硬边界规则（本人承诺） | 原设想为"规则清单"功能：用户写入"我一定不会吃什么"，作为长期上下文由蛇的视角反复提醒/劝诫用户"要忍住"。否决原因：**太负向**——说教式劝诫与产品"正向反馈"的核心调性相悖 |
| 2026-09-27 | 喂食后的反悔/撤回机制 | 原设想：东西喂进蛇嘴巴后用户仍可反悔取出。否决原因：① 不符合事实逻辑——进了蛇嘴的东西吐不出来；② 只是个小功能；③ "可反悔"给用户留了退路，削弱承诺感。**现行设计**：明确告知"进蛇口的东西不能吐出"，让用户切实落下心愿；反悔窗口只存在于投喂动作发生前的当下那一刻 |
| 2026-09-27 | 打卡/连续记录类设计（日历按天呈现、streak 闭环） | 原设想：日历按天呈现，用户每天打卡才能达成闭环。否决原因：这是个小产品，用户很难每天连续进来；断签后日历上全是缺失，**未完成感会转化为负向情绪**，用户越来越不想用。产品遵循"来了就有收获，不来无惩罚"的松散陪伴原则 |
